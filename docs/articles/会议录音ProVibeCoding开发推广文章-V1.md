# 会议录音 Pro Vibe Coding 开发推广文章 V1

## 写作结构建议

这篇文章建议先讲软件，再讲开发过程。

原因很简单：读者先要知道这个软件解决什么问题，才会关心它是怎么被做出来的。开头先从 Mac 用户常见的录音痛点进入，讲「会议录音 Pro」解决了什么。第二部分再讲 Vibe Coding 的开发过程：从一开始想做大而全，到中途把功能收回来；从反复让 AI review，到最后把可用性标准、自动化测试和发布目标写清楚。

可以分成两个大章节：

1. **我为什么做这个录音软件**：讲痛点、功能、适合谁用。
2. **我怎么用 Vibe Coding 把它做出来**：讲需求收缩、Agent 规则、测试门槛、权限引导和发布标准。

## 正文草稿

# 我用 Vibe Coding 做了一个 Mac 会议录音软件

我最近做了一个很小的 Mac 软件，叫「会议录音 Pro」。

它不是会议 AI，也不是音频工作站。它只解决一件事：在 Mac 上更方便、更稳定地录下会议声音。

我自己一直有这个需求。开会、访谈、复盘、听课，有些内容当场听完觉得记住了，过几天再回头看，很多细节都忘了。录音是最稳的原始记录。但我用 Mac 自带语音备忘录时，经常遇到几个问题。

第一个问题是文件不好管理。语音备忘录的数据会跟着 iCloud 同步，实际文件路径藏得很深。时间长了之后，iCloud 里会堆很多录音，想找、想迁移、想整理，都不顺手。

第二个问题是启动不够快。语音备忘录没有全局快捷键。开会时如果临时想录，需要切应用、找窗口、点开始，很打断。

第三个问题是容易忘记关。有时候会后忙着处理别的事情，录音一直挂在那里，最后录出十几个小时甚至二十几个小时。后面再剪掉无用部分，又是一件麻烦事。

第四个问题是线上会议。现在很多会议都是戴耳机开的，普通麦克风录音往往只能录到自己说话，对方的声音在耳机里，录音文件里没有。真到复盘的时候，文件就废了一半。

所以我做了「会议录音 Pro」。它常驻在菜单栏，不占 Dock。需要录音时，可以点菜单，也可以按全局快捷键。它支持三种录音来源：麦克风、系统声音、麦克风加系统声音。戴着耳机开会时，也能把自己和对方的声音一起录下来。

我还给它加了几个自己很需要的功能：最长录音时长，避免会后忘记关；定时录音，解决固定会议忘记录的问题；M4A 和 MP3 输出，前者适合本地保存，后者适合上传到一些只接受 MP3 的转写服务。录音过程里先保存稳定的 M4A，结束后再按设置转成 MP3。

还有本地保存和开源。录音文件只保存在用户指定的本地目录，不需要账号。录音本身不需要网络，也不会上传到云端。自动更新会访问 GitHub Releases，但不会上传录音内容。项目准备开源，愿意看的用户可以自己检查它做了什么。

这些是产品本身。另一个我想分享的是，这个软件是我用 Vibe Coding 做出来的。

我说的 Vibe Coding，不是随口对 AI 说一句「帮我做个软件」，然后等它把事情做完。一开始，我也以为这东西很简单：按开始，按停止，保存一个文件，应该很快就能做好。结果做着做着，功能越来越多：先是录音，后来想加转写；转完文字，又想加总结；再往后，又会自然想到会议列表、录音管理、文件夹管理、搜索、标签、导出。每一步看起来都合理，但放在一起，产品很快就变成一个大系统。

中途我重新 review 了一遍功能，最后决定把大部分东西拿掉。

我的想法也有一点变化。AI 时代，很多软件不一定要把整条工作链路都吃下来。录音、转写、总结、知识管理、文件管理，这些事情可以拆开。每个环节都可以用自己最喜欢、最顺手的软件。一个小工具只要把其中一环做稳，就已经有价值。

所以「会议录音 Pro」最后只保留录音这件事里的关键能力：快速开始、双向录音、定时录音、最长时长、本地文件、M4A/MP3、权限引导、打包分发。它不做转写，不做总结，也不做庞大的录音资料库。

这次开发里，我花了很多时间跟 AI 反复 review 代码。

我会问它：你看看这个项目有没有问题？有没有丢录音的风险？有没有权限问题？有没有打包问题？有没有系统声音录不到的问题？

AI 每次都能找出一些问题，也会说已经修了。但我作为产品使用者和非专业音频工程师，并不能只凭一句「修好了」就放心。录音软件最怕的是平时看不出来、关键时候才暴露的问题：录了一小时，文件只有十几分钟；系统声音其实没录进去；MP3 后缀有了，文件不能用；本机能打开，别人下载后过不了 macOS 安全校验。

后来我意识到，不能一直靠「再 review 一遍」推进。需要先定义什么叫可用。

于是我让 AI 帮我一起把项目规则写进 `AGENTS.md`，又补了几份文档：稳定交付标准、功能清单、测试用例、发布检查清单、回归测试流程。里面最有用的是阻断级别：会丢录音、文件损坏、应用打不开、DMG 无法安装，是 P0；麦克风录音、系统声音录音、混合录音、MP3 输出、定时自动录音这些常用路径失败，是 P1。P0/P1 没清零，就不能说可以交付。

它还写清楚了停止继续排查的条件：完整 QA 通过，代码 review 没有 P0/P1，人工环境项已经记录，Git 里有可回滚提交，工作区没有相关未提交改动。

这一步之后，开发节奏就稳定多了。以前是我不断问「你再看看还有没有问题」。后来变成看标准：哪些测过了，哪些没测过，当前是否达到最初定义的目标。这样我才知道什么时候应该继续修，什么时候可以停下来。

测试也是中途才真正成体系的。

录音软件的测试很麻烦。它不只是点一下按钮看有没有反应，还要测麦克风、系统声音、混合录音、暂停继续、连续录音、定时录音、MP3 转码、录音中退出、权限缺失、打包产物。每改一次都人工走一遍，成本很高，也很容易漏。

后来我把测试逻辑也交给 Agent 固化下来。

项目里现在有一键 QA 脚本：`scripts/run_full_qa.sh`。它会先打出 Release 包，再用打包后的应用跑测试，覆盖设置回读、麦克风录音、暂停继续、连续录音、系统声音、混合音源、定时自动录音，还会检查 DMG、签名、录音文件和日志。

我还加了一个可听的专项测试。脚本会生成两段测试音频：一段作为系统声音，一段作为麦克风声音。然后分别跑三种模式：直录系统声音、直录麦克风、系统加麦克风。跑完之后，它会输出原始录音和增益后的试听文件。这样我不只是看测试报告，还能真的听一下：三种模式到底有没有录进去。

这件事极大降低了后续修改的心理成本。以前改完一个地方，我不知道会不会影响别的路径。现在大部分路径可以自动测掉，剩下菜单栏视觉、系统授权、设备插拔、登录项这类强交互场景，再人工补测。

还有一个小功能，我挺喜欢，就是权限引导。

macOS 的权限设置对普通用户并不友好。录系统声音需要开启「屏幕与系统音频录制」权限，但系统设置层级很深。早期我只是跳到系统设置页面，后来在 Codex 引导授权的体验里看到一种更清楚的交互：自动打开对应设置页，再用悬浮引导告诉用户应该把哪个应用打开。

我把这个思路结合开源项目 PermissionFlow 引入到软件里。现在用户选择系统声音或混合录音时，如果还没授权，软件会触发权限引导。它不会一启动就要权限，只有用户真的选择系统声音相关模式时才请求。

最后是发布。

这也是我后来才补上的部分。做 Mac 软件，自己能跑起来和别人能顺利安装，是两回事。这个项目不走 Mac App Store，而是开源仓库加独立 DMG 分发。所以我把发布目标也写进文档：本机验证包要能通过 `./build_dmg.sh`；正式公开分发要使用 Developer ID 签名，通过 notarization、stapler validation 和 Gatekeeper；版本发布时还要同步上传 DMG 和 `appcast.xml`。

回头看，这次 Vibe Coding 留给我的主要经验，是我逐渐学会了怎么跟 AI 协作。

需求不能只写一句话，要写清边界。功能不能一直加，要定期收缩。质量不能靠反复 review，要变成测试和发布标准。AI 说修好了也不够，要有录音文件、测试报告、打包校验和可回滚提交。

「会议录音 Pro」现在就是这样一个小工具。它不试图接管你的会议工作流，只负责把会议声音本地、稳定地录下来。后面你想用哪个软件转写、总结、整理，都可以自己选择。

如果你也经常在 Mac 上开会，遇到过忘记录、忘记关、找不到文件、耳机会议只录到自己声音这些问题，可以试试它。使用中遇到问题，也可以直接提 bug，我会继续按这套标准修。
