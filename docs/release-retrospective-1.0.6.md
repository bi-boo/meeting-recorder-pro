## 问题与处理

### 1. 本机是 1.0.6，GitHub 仍显示 1.0.5

**现象**

项目代码、应用和 `v1.0.6` 标签已经更新，但 GitHub Releases 页面仍把 1.0.5 显示为 Latest。

**根因**

以下四个状态彼此独立，更新其中一个不会自动更新其他状态：

1. `CFBundleShortVersionString`
2. Git 主分支
3. Git 标签
4. GitHub Release

当时只完成了前三项，尚未创建 1.0.6 的 GitHub Release。

**处理**

- 将主分支推送到 `a7cca7c`。
- 将远程 `v1.0.6` 标签更新到同一提交。
- 完成 Apple 公证后创建正式 GitHub Release。
- 从 GitHub 回下载三个资产，重新核对哈希和签名状态。

**后续规则**

版本发布完成必须同时回读主分支、标签、Release 和 `latest` 自动更新地址。只看到标签存在，不能判断正式版本已经发布。

### 2. 对外版本号与内部构建号混在一起展示

**现象**

应用曾显示类似 `1.0.5 (6)` 的版本，其中括号内数字容易被理解成对外版本的一部分。

**根因**

macOS 使用两套版本字段：

- `CFBundleShortVersionString`：对外版本号，如 `1.0.6`。
- `CFBundleVersion`：内部递增构建号，Sparkle 用它判断更新先后，如 `7`。

两者都属于标准字段，但不应在普通用户界面中并列展示。

**处理**

- 关于页面只显示 `1.0.6`。
- 内部构建号继续保留在 App 元数据和 `appcast.xml` 中，不进入普通界面。

**后续规则**

对外界面、Release 标题和文件说明只写短版本号；构建号仅用于工程、诊断和自动更新排序。

### 3. 菜单栏录音计时宽度跳动

**现象**

菜单栏计时数字变化时，字符实际宽度不同，导致菜单栏占位一会儿宽、一会儿窄。

**根因**

计时文本使用按内容自然伸缩的布局，没有为完整时间格式预留固定宽度。

**处理**

为录音计时区域设置固定占位宽度，使秒数变化不再改变菜单栏整体宽度。

**后续规则**

菜单栏中的计时、速率、百分比等高频变化数字必须使用固定宽度或等宽数字，不允许由内容驱动菜单栏反复重排。

### 4. 正常的启动初始化被误判为设备切换

**现象**

录音启动时出现「录音启动失败，输入设备格式在启动后仍持续变化」提示。用户并未主动切换设备。

**根因**

macOS 音频路由在启动阶段可能经历多轮格式和默认设备回调。旧实现只要在首次初始化后再次看到格式变化，就按失败处理；这个条件比真实异常更严格。

设备切换策略也没有充分区分两个阶段：

- `.starting`：系统仍在完成路由协商，允许有限时间内变化。
- `.recording`：录音已稳定，实际切换输入设备时应中断并保存。

**处理**

- 启动阶段增加至少 1.5 秒的稳定观察窗口，每 0.6 秒复查。
- 稳定条件同时检查采样格式和实际输入设备 ID。
- 当前默认设备未知时继续等待，不再立刻判定为切换。
- 启动阶段发现实际路由与默认设备不一致时重建采集链路。
- 进入 `.recording` 后，只有已记录设备 ID 和当前设备 ID 都已知且确实不同，才执行中断并保存。
- 设备被移除仍由设备列表变化路径独立处理。

**验证**

新增启动稳定窗口、设备 ID 匹配、未知设备 ID 和真实切换策略测试，单元测试最终为 29/29 通过。

### 5. 音频集成测试自动选中了静音设备

**现象**

真实录音集成测试出现 4 项通过、8 项失败。`Wireless Mic Rx` 生成的麦克风和混合录音接近绝对静音，约为 `-91 dB`。

**根因**

测试脚本按设备排序自动选择设备组合，没有先确认设备是否真的有声音。USB 接收器虽然被系统识别，但发射端未工作，因此「设备存在」不等于「设备可录音」。

同时，系统在测试开始后把默认输入从内置麦克风自动切回 USB 接收器，暴露了启动路由稳定逻辑的问题。

**处理**

- 测试脚本新增 `--input-pair SOURCE TARGET` 和 `--output-pair SOURCE TARGET`。
- 测试过程中按 AVFoundation 稳定设备 ID 固定来源和目标设备。
- 基础麦克风、混合录音、切换前录音和切换后重启分别固定到指定设备。
- 增加设备列表与轻量音量预检，先确认设备可用，再运行完整测试。

**后续规则**

测试设备选择必须同时满足「被系统识别」和「音量预检非静音」。禁止仅按设备名称或排序自动挑选第二个设备。

### 6. 测试次数过多，代码失败与环境失败没有及时分开

**现象**

同一轮发布中多次构建和录音，用户感受到「一直在重复测试」。

**根因**

- 每次代码修复都会改变最终可执行文件，旧报告不能作为新二进制的发布证据。
- 音频硬件不可用时仍进入了较重的集成测试，没有先做快速设备和音量预检。
- 代码缺陷、硬件静音、设备断开和公证凭据失败没有在第一时间分层说明。

**后续顺序**

1. 单元测试验证纯逻辑。
2. 列出音频设备并做 3 秒以内的音量预检。
3. 只在硬件条件满足时运行一次真实集成测试。
4. 代码冻结后运行一次完整 QA。
5. 安装与最终 DMG 完全一致的 App，再生成发布证据。
6. 公证前先验证 Keychain 公证配置，避免构建完成后才发现凭据失效。

相同环境条件没有变化时，不重复运行同一测试。

### 7. 测试录音的交付入口不够直接

**现象**

自动化报告生成了可听录音，但结果汇报没有始终把录音目录作为第一层交付物，导致需要再次查找文件夹。

**处理与规则**

每次录音测试汇报必须包含：

- `passed / failed / skipped`
- `report.json` 或 `report.md`
- 可直接打开的录音目录
- 失败或跳过原因

对音质、静音和混音结果，数值检查不能代替人工试听入口。

### 8. 同步冲突文件干扰构建与提交

**现象**

Synology Drive 生成了多份 `_Conflict.swift` 文件，存在被编译或误提交的风险。

**处理**

确认原始受跟踪文件为当前版本后，将冲突副本移动到项目外的临时备份目录，没有提交到 Git。

**后续规则**

构建和提交前固定执行：

```bash
find SimpleRecorder -name '*Conflict.swift' -print
```

发现冲突文件时先比较内容，再恢复到唯一受跟踪路径；不能直接批量删除或提交冲突副本。

### 9. 扩展属性清理曾破坏发布签名顺序

**现象**

发布包签名验证曾受 macOS 扩展属性影响。

**根因**

扩展属性必须在签名前清理。签名后再次执行递归 `xattr -cr` 可能改变签名覆盖的包内容。

**处理**

构建脚本改为在代码签名前清理应用扩展属性，签名完成后只执行验证，不再修改包内容。

**后续规则**

发布包处理顺序固定为「构建 → 清理扩展属性 → 签名 → 验签 → 制作 DMG → DMG 签名 → 公证 → Stapler → Gatekeeper」。

### 10. Apple 公证连续返回 401

**现象**

旧 App 专用密码和第一次重新输入的新密码均返回：

```text
HTTP 401: Invalid credentials
```

**排查结论**

- Developer ID 证书有效。
- Xcode 登录账号属于对应开发团队，角色为 Admin。
- App 专用密码可以同时存在多个，连字符属于标准格式，不是失败原因。
- 最后一次通过 `notarytool` 隐藏交互输入的新密码验证成功，并保存到本机 Keychain 的 `notarytool-profile`。

前两次失败最可能来自旧密码失效、输入值不一致，或复制时混入不可见字符。Apple 的 401 不能单独区分这些原因。

**后续规则**

- 密码只通过系统隐藏输入框或 `notarytool` 安全提示输入。
- 不把 App 专用密码写入命令行参数、项目文件、日志或聊天。
- 发布前先执行一次只读凭据验证，再开始长时间构建。
- App 专用密码如果曾出现在聊天或其他可回读记录中，发布后立即撤销，并用安全输入方式更新 Keychain 配置。

### 11. 安装前误判应用未运行

**现象**

安装公证版前的进程检查一度返回「未运行」，随后发布 QA 发现旧实例仍在运行，并持有一个正在写入的 `.m4a` 文件。

**根因**

沙箱中的 `pgrep`、`ps` 可见性和路径过滤结果不可靠。应用被移动到备份路径后，运行中进程的显示路径与磁盘实际位置也可能不一致。单纯匹配应用路径不足以证明应用未运行。

磁盘上的 App 当时已经被替换，但旧进程继续驻留并写入录音。此次录音没有被中断，后续 QA 也正确拒绝停止该实例，但该操作本身存在录音丢失风险。

**后续硬门禁**

安装或替换 App 前必须同时执行：

1. 在系统权限环境检查 `SimpleRecorder` 进程名和 PID。
2. 使用 `lsof` 检查进程是否持有 `.m4a`、`.mp3`、`.caf` 或临时录音文件。
3. 检查应用日志中的最近录音状态。
4. 只要存在录音中实例，就停止安装流程，等待录音正常结束并退出应用。
5. 安装后比较 DMG 内 App、构建 App 和 `/Applications` App 的可执行文件 SHA-256。

不能因为「替换磁盘文件通常不会立刻终止进程」就接受运行中更新。

### 12. 发布门禁与明确发布决定冲突

**现象**

项目正式发布脚本要求当前最终二进制具有通过的双设备真实录音报告。本机最后只检测到一个输入设备，发布负责人明确决定跳过第二麦克风验证并直接发布。

发布前的自动化 QA 又检测到真实录音正在进行，因此主动终止，没有停止录音。最终 Release 使用已公证并通过 Gatekeeper 的固定 DMG 手动创建，没有伪造集成测试报告。

**已记录的发布例外**

- 双输入设备切换专项测试未在最终公证二进制上执行。
- 最终 DMG 的自动化 QA 因运行中真实录音而未完成。
- 此前同一提交的完整 QA 结果为 `passed=8, failed=0, skipped=1`；跳过项为人工环境检查。
- 发布包本身完成了 Developer ID 签名、Apple 公证、Stapler、Gatekeeper、DMG 校验、远程回下载和资产哈希核对。

**后续改进**

发布脚本应增加显式的发布例外文件，而不是依赖手工绕过：

- 写明跳过场景、原因、批准人、时间和风险判断。
- 禁止把例外伪装成测试通过。
- P0/P1、签名、公证、Gatekeeper 和资产一致性仍不可豁免。
- 发布完成后把例外写入发布证据，并保留后补测试入口。

## 固化后的发布顺序

以后发布版本按以下顺序执行：

1. 确认短版本号和构建号，并检查关于页面只显示短版本号。
2. 检查 Git 工作区、同步冲突文件、主分支和标签状态。
3. 确认应用未运行、未录音，再安装候选 App。
4. 运行单元测试。
5. 预检音频设备和实际音量；条件满足后只运行一次真实录音集成测试。
6. 运行完整 QA，并提供可点击的录音目录。
7. 用 Keychain profile 预检 Apple 公证凭据。
8. 生成固定 Release App 和 DMG，完成签名、公证、Stapler 与 Gatekeeper。
9. 安装 DMG 内同一份 App，核对可执行文件 SHA-256。
10. 推送主分支，确认本地和远程标签均指向 HEAD。
11. 创建 GitHub Release，上传 DMG、`appcast.xml` 和 LAME 源码。
12. 从 GitHub 回下载资产，复查哈希、公证、Gatekeeper 和 `latest` 自动更新地址。

任何一步生成了新二进制，后续证据必须绑定新二进制，不能继续使用旧可执行文件的报告。
